# OfficeCare AI 总体升级路线：AI 应用开发求职方向

总体路线草案；用户已授权启动 M0，其余范围待逐项确认。用户目标为 AI 应用开发，侧重 RAG / Agent；暂不限定完成时间。本页统一维护总体路线，具体开发状态仍见 [STATUS](../STATUS.md)。里程碑编号用于规划，不表示已开始新的开发阶段。

## 目标与用户看到的效果

将项目逐步完善为“面向办公设备售后的可信知识问答与服务 Agent”：导入产品手册，限定品牌和型号检索，给出可核对的诊断建议，按需查询维修业务信息，形成候选方案，经用户确认后创建或推进工单。

目标对应三类可展示成果：

1. 能解释并用实验验证的 RAG：文档结构、检索、排序、引用、拒答和评测相互对应。
2. 能处理异常与人工介入的 Agent：工具调用、业务状态、检查点、幂等和权限边界清楚。
3. 可复现的完整作品：演示流程、运行方式、质量与成本数据、个人贡献和技术取舍有据可查。

原项目已有能力与本人后续完成的改动分开记录；简历写实际实现和验证过的部分，效果数字由固定条件下的实测产生。

## 范围与不做

- 本轮交付总体规划，不实施功能开发；现有阶段 02 / 03 的验收状态保持原样。
- 沿用 Java / FastAPI / Vue 的职责边界：Java 管权限、业务和文档版本，FastAPI 管 RAG / Agent，前端呈现过程、证据与确认动作。
- 主线学习投入集中在检索、Agent 和评测；工程可靠性、权限与交付贯穿各阶段。
- 库版本和模型升级按兼容性、实际问题与对照效果决定；先保留现有 Spring Boot、LangChain / LangGraph、Milvus 等基础。
- Milvus Schema、Embedding 维度或索引空间调整，必须单独设计并经确认，写明新旧版本切换和回滚方式。
- 图片报修、MCP、跨会话长期记忆、多 Agent 列为后续选做；每项先验证业务用途、数据授权和资源要求。

### 总体里程碑

每次只推进一个里程碑；对应设计确认后开发，验收后进入下一项。新增正式阶段的编号在启动时确定。

| 顺序 | 单一目标 | 主要优化、升级或新增内容 | 验收成果 | 学习及简历材料 |
|---|---|---|---|---|
| M0 | 收口工程基线 | 明确 GitHub 工作基线；完成阶段 02 用户验收；核对前后端重试的 turnId；建立最小构建和本地测试 CI | 已知并发、超时、落库失败场景可复现；主干构建与测试结果清楚 | 幂等、事务边界、跨存储恢复、故障定位 |
| M1 | 建立可信的 RAG 质量基线 | 在阶段 03 范围内修连续型号边界与守卫冲突；核准题目和标准证据；正负例分开统计；拆分开发题和保留题 | 已知跨型号回归无错误引用；错误答案、否定句和无关菜单不再被误判通过；形成可复跑基线 | 评测设计、数据质量、引用归因与消融实验 |
| M2 | 保留文档结构与来源 | 分离章节、型号组、表格行与续表；补齐页码和段落锚点；验证文档 / 解析 / 索引版本一致性和删除失效 | 典型混合型号表格能准确定位；发布、重新索引和回退可核对；旧版本不混入当前检索 | 非结构化数据处理、结构化分块、索引治理 |
| M3 | 升级检索与排序 | 对比现有词法扫描与 BM25 稀疏召回；受控故障同义检索；RRF 后增加 Reranker 实验；校准拒答与上下文选择 | 固定语料与保留题上比较命中、排序、引用、延迟和费用，明确哪些升级值得保留 | 多阶段检索、中文检索、重排、质量与成本取舍 |
| M4 | 建成可恢复的业务 Agent | 增加经 Java 授权的维修历史等动态查询；结构化维护已确认事实、排查步骤和观察；设计人工审批暂停 / 恢复；候选绑定基础版本 | 工具异常、进程重启、重复恢复和过期确认有确定行为；正式写入经过用户确认和服务端复核 | Tool Calling、状态图、持久执行、人机协作与业务边界 |
| M5 | 完善用户交互与证据展示 | SSE 流式回答与运行状态；失败重试 / 断线恢复；PDF 原文页定位，具备锚点时再做精确高亮；展示用户可读的工具执行结果 | 用户能看到进度、核对证据、恢复失败请求并完成报修；运行展示不暴露内部推理过程 | 流式协议、前后端协作、可解释交互 |
| M6 | 建立反馈与知识回流 | 将现有点踩扩展为待审核问题；人工纠正答案；将已核实维修结果整理为案例 / FAQ；审核后发布并补回归题 | 从一次错误回答走完“反馈—审核—修正—发布—再次检索”闭环，保留来源和版本 | 人工反馈、知识生命周期、业务数据到评测集 |
| M7 | 控制运行成本与服务质量 | 统一请求 / 任务追踪；记录检索、模型、工具与落库耗时；统计 Token 与估算费用；细分 TLS / 超时 / 限流等错误；校验缓存和并发配额 | 有可解释的质量、延迟、成功率和费用看板；同一条件下完成优化前后对照 | LLM 应用观测、性能分析、缓存与成本治理 |
| M8 | 形成求职交付版本 | 经用户安排后补部署验收；合成演示数据、启动及恢复流程；完善公开 README / 工程导读、演示录像和个人贡献说明 | 按文档可复现演示；能展示正常流程和故障恢复；形成可核实的简历与面试材料 | 系统设计表达、工程交付、技术复盘 |

M0–M5 完成后可整理第一版可演示简历项目；M6–M8 形成更完整的学习与求职作品。各阶段按实际复杂度拆分设计，不预设完成日期。

### 技术升级原则与官方依据

- 保留现有 Java 17 / Spring Boot 3、Vue 3、FastAPI、LangChain / LangGraph、Milvus、MySQL / PostgreSQL / Redis、RabbitMQ 结构。新增复杂度须对应已测问题或明确功能。
- Milvus 原生 BM25 需要相应文本分析、稀疏字段和索引设计；先核实实际服务端版本与中文分词效果，再设计 Schema / 新集合、切换和回滚。[Milvus 全文检索文档](https://milvus.io/docs/full-text-search.md)
- 可恢复审批基于持久化检查点与显式暂停 / 恢复；节点可能重新执行，正式业务副作用仍由 Java 幂等与版本检查保护。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[暂停与恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)
- 官方最新文档可能包含当前锁定依赖没有的接口，设计时以仓库安装版本验证兼容性；依赖和锁文件变更单独列明。
- CI 初期运行构建、本地确定性测试和必要静态检查；真实模型评测单独触发并记录所用数据、模型与费用范围。[GitHub Actions Maven 文档](https://docs.github.com/en/actions/tutorials/build-and-test-code/java-with-maven)

## 内部步骤

1. 用户确认总体路线与核心交付边界；正式开发仍先收口当前阶段 02。
2. 每个里程碑启动时，只为当前阶段写目标、范围、设计、依赖 / 迁移影响和验收方式。
3. 在独立 worktree 开发，自检后按用户决定安排独立测试，再由用户验收。
4. 每阶段完成一条可演示链路，并保留问题、实现取舍和实测前后对照。
5. 提交、推送和合并按用户指令执行；阶段结果、STATUS 和必要决策记录按仓库规则更新。

## 验证方式

- 学习成果：每个核心模块能解释输入、状态、失败分支、边界和选型原因，并能从源码定位。
- RAG：固定语料与版本，使用开发题 / 保留题，核对正确引用、拒答、跨型号及过期文档，报告检索与最终答案两层结果。
- Agent：验证工具权限、参数、异常恢复、重复请求、重复确认、过期候选和用户已确认事实的保护。
- 运行表现：相同模型、语料、并发和环境下记录 P50 / P95、调用成功率、Token 与估算费用；目标值在各阶段设计中确认，不预写效果提升数字。
- 独立验收测试若安排，按仓库规则保留 15–30 个有意义的核心用例；所有写入测试使用隔离测试资源。
- 演示：导入手册与提问核对引用；多轮追问与业务查询；人工确认工单；反馈修正知识；演示一条可恢复失败流程。
